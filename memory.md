# Memory Layout and Garbage Collection (GC) — सूत्र (Sutra)

This document describes the memory structures, heap allocations, object layouts, and garbage collection mechanisms of the Sutra language runtime.

---

## 1. Heap Objects Memory Layout

All dynamic runtime instances (strings, arrays, classes, and dictionaries) are allocated on a garbage-collected heap. Each allocation contains headers prefixing the raw payload:

### 1.1 String Layout (`GC_TYPE_STRING` / `DataType::PAATH`)
Strings are dynamic UTF-8 byte arrays, structured with capacity and length headers:
```text
+---------------------+-------------------+------------------------+-------------------+
| capacity (8 bytes)  |  length (8 bytes) | UTF-8 chars (N bytes)  | '\0' (1 byte null) |
+---------------------+-------------------+------------------------+-------------------+
0                     8                   16                       16 + N
```
* **Capacity (uint64_t)**: The reserved size of the character buffer.
* **Length (uint64_t)**: The active number of UTF-8 encoded bytes in the string value.
* **Payload**: Raw UTF-8 bytes followed by a single null terminator byte `\0`.

### 1.2 Array/List Layout (`GC_TYPE_ARRAY` / `DataType::UNKNOWN`, "Array")
Lists represent dynamically resizable sequences storing dynamic values:
```text
+---------------------+-------------------+--------------------------------------------+
| capacity (8 bytes)  |  length (8 bytes) | element_0 (8B) | ... | element_N-1 (8B)    |
+---------------------+-------------------+--------------------------------------------+
0                     8                   16                                           16 + N*8
```
* **Capacity (uint64_t)**: The maximum number of elements the list can hold before triggering a realloc resize.
* **Length (uint64_t)**: The current active count of elements.
* **Payload**: Sequentially indexed 8-byte elements. Each element is either a raw integer, floating-point bits, or a pointer referencing another heap object.

### 1.3 Object/Class Instance Layout (`GC_TYPE_OBJECT` / `DataType::UNKNOWN`, "Object")
Class instances allocate memory dynamically to house declared object property variables:
```text
+---------------------+-------------------+--------------------------------------------+
| capacity (8 bytes)  |  length (8 bytes) | field_0 (8B) | ... | field_N-1 (8B)        |
+---------------------+-------------------+--------------------------------------------+
0                     8                   16
```
* **Capacity (uint64_t)**: Reserved field slots.
* **Length (uint64_t)**: Number of declared fields in class layout.
* **Payload**: Active values of property fields stored as 8-byte elements.

### 1.4 Dictionary Layout (`GC_TYPE_DICTIONARY` / `DataType::SHABDAKOSH`)
Dictionaries use a dynamically sized hash table header pointing to key-value entries:
```text
+---------------------+-------------------+--------------------------------------------+
| capacity (8 bytes)  |  length (8 bytes) | entries_pointer (8 bytes)                  |
+---------------------+-------------------+--------------------------------------------+
0                     8                   16                                           24
```
* **Capacity (uint64_t)**: Reserved capacity of the hash bucket array.
* **Length (uint64_t)**: Active number of key-value elements mapped in the dictionary.
* **Entries Pointer**: A pointer referencing a separate memory buffer containing array structures of key-value records:
  - Each entry occupies 16 bytes: `[key_pointer (8 bytes)] [value_element (8 bytes)]`.

## 2. Garbage Collection (GC) Architecture

Sutra uses a custom **Mark-and-Sweep Garbage Collector** that runs in two configurations depending on execution mode:

### 2.1 AST Interpreter GC
* **Roots**: Scanned directly from active C++ execution environments (`Environment*` scopes) and active exception structures (`m_active_exceptions`).
* **Implementation**: [`GarbageCollector::collect()`](file:///d:/my%20project/सूत्र/संकलक/src/स्मृतिसंग्राहक.cpp#L52-L131). Scans environment scopes, marks reachable addresses, and calls the C++ HeapManager sweep function to free memory.

### 2.2 Native Code Executable GC
* **Roots**: Scanned using a **Shadow Stack** structure maintained during native binary executions.
* **Shadow Stack**: The assembly code generated by the compiler inserts local environment allocations into a root pointer stack array (`gc_roots` in `संकलक/src/compiler/sutra_runtime.c`) via runtime calls:
  - `sutra_gc_push_root(void* addr)`: Pushes a local variable address onto the root registry shadow stack during function prologue setups.
  - `sutra_gc_pop_root(void* addr)`: Pops the address from the registry during function epilogue returns.
* **Implementation**: [`sutra_native_gc_collect()`](file:///d:/my%20project/सूत्र/संकलक/src/runtime_api.cpp#L151-L196). It is triggered by the runtime to perform mark-and-sweep collections over tracked native allocations.

## 3. GC Mark-and-Sweep Phases

```text
               1. RESET MARKS
       (Clear marked flag on all tracked buffers)
                       ↓
               2. MARK PHASE
       (Scan roots & trace child pointers recursively)
                       ↓
               3. SWEEP PHASE
       (Free unmarked heap blocks & update GC telemetry)
```

### 3.1 Reset Phase
All registered memory blocks in the heap database have their marked flag reset to `0` / false.

### 3.2 Mark Phase
The GC starts tracing from active roots. It recursively walks reachable child pointers based on the allocation metadata type:
* **`GC_TYPE_ARRAY`**: Dereferences elements offset arrays, marking child heap pointers.
* **`GC_TYPE_OBJECT`**: Dereferences object field offsets, tracing child references.
* **`GC_TYPE_DICTIONARY`**: Dereferences the entries array, tracing child keys and values.

### 3.3 Sweep Phase
Allocated memory blocks that did not receive a mark are freed:
* For `GC_TYPE_DICTIONARY` allocations, the sub-entries array is freed before freeing the dictionary header.
* Standard memory allocations are reclaimed using native `free()`.
* Telemetry variables (`live_allocs`, `collected_objects`, `bytes_reclaimed`) are updated to reflect the cleaned heap size.
